# 🌿 Регламент найменування Git-гілок та робочого процесу (Duck Verse)

Кожен розробник у команді (учні та ментори) зобов'язаний суворо дотримуватися стандартів найменування гілок та процесу розробки. Це забезпечує автоматичну інтеграцію з **Jira**, запуск перевірок у **GitHub Actions** та швидкий рев'ю коду.

---

## 📌 1. Стандарт назви гілок (Branch Naming Convention)

Формат назви гілки:
```bash
<type>/<JIRA-KEY>-<короткий-опис-англійською-через-дефіс>
```

### Дозволені префікси (`<type>`):
* `feature/` — нова фіча, гра, компонент (наприклад, `feature/SCRUM-18-flappy-duck`)
* `fix/` — виправлення багу чи помилки (наприклад, `fix/SCRUM-10-collision-bug`)
* `refactor/` — покращення архітектури або коду без зміни функціоналу
* `docs/` — оновлення документації, інструкцій

## 🔄 3. Покроковий цикл розробника (Terminal Cheat-Sheet)

### Крок 1. Підготовка перед стартом (тільки від свіжого main)
```bash
git checkout main
git pull origin main
```

### Крок 2. Створення робочої гілки під задачу
```bash
# Приклад для задачі SCRUM-18:
git checkout -b feature/SCRUM-18-flappy-duck
```

### Крок 3. Написання коду та локальна перевірка
Під час роботи або запитів до AI-агента завжди перевіряємо працездатність:
```bash
npm run dev
```
Перед комітом **обов'язково** запускаємо збірку проекту:
```bash
npm run build
```
*(Якщо збірка видає хоч одну помилку — комітити заборонено!)*

### Крок 4. Збереження та Smart Commit для Jira
Кожен коміт має містити номер задачі:
```bash
git add .
git commit -m "feat(SCRUM-18): реалізовано стрибок качечки та перевірку колізій"
```

### Крок 5. Відправка на GitHub та відкриття Pull Request
```bash
git push -u origin feature/SCRUM-18-flappy-duck
```
Після відправки гілки:
1. Переходимо у [GitHub Duck Verse Pulls](https://github.com/greenyarik0505-jpg/duck-verse/pulls).
2. Натискаємо **Compare & pull request**.
3. Заповнюємо чек-лист у створеному шаблоні PR.
4. Перетягуємо задачу в Jira в колонку **`In Review`**.
5. Очікуємо перевірки Team Lead і мерджу!
